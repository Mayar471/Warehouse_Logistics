# رد قيمة البضائع للعميل نقدًا

12 أكتوبر 2026 — ترحيل 20، عرض محلي بعملة SYP.

## السياسة التجريبية والنطاق

يعتمد المتجر المالك رد **كامل قيمة البضائع المحصلة** بعد وصول الإرجاع التجاري وفحص جميع قطعه وإرسال رده النهائي للعميل. راجع [سبب العميل ورد المتجر](./RETURN-REASON-AND-MERCHANT-REPLY.md). رسوم التوصيل لا تُرد في هذه الشريحة. نتيجة صلاحية القطع لا تحدد حق العميل ماليًا تلقائيًا؛ المتجر يراجع القرار ويعتمد رد القيمة كاملة مع سبب ومرجع. سياسة الرسوم التجارية والإرجاع الجزئي والدفع الإلكتروني تحتاج عقودًا لاحقة، ولا يُستنتج منها اعتماد سياسة تشغيل فعلية.

يشترط وصول تحصيل الطلب كاملًا إلى العمليات دون فرق مفتوح. إذا صُرفت مستحقات المتجر، تُستعاد وفق مسار استرداد الدفعة القائم قبل اعتماد رد العميل. يُرفض الرد عند وجود حجز/عهدة/دفعة متجر فعالة أو حوالة في مسار الرجوع. ويمنع قرار الرد المعتمد غير الملغى صرف مستحق الطلب مجددًا وإرجاع حوالة تمويله؛ قواعد الخادم والمعاملة هي الحماية النهائية عند التزامن.

## الخطوات والقيود

| الإجراء | صاحب الإقرار | الحالة التالية | الأثر المالي |
|---|---|---|---|
| request | المتجر المالك | requested | اعتماد ثابت للقيمة؛ دون خروج نقد أو إغلاق دين |
| reserve | العمليات | reserved | تخصيص نقد التحصيل نفسه؛ دون حركة نقد |
| release | العمليات | released | إقرار تسليم النقد للعميل؛ ينتقل إلى عهدة رد العميل |
| confirm | العميل مالك الطلب | confirmed | إقرار مستقل باستلام كامل المبلغ؛ تنتهي عهدة الرد ومستحق البضائع |
| report | العميل مالك الطلب | released مع فرق مفتوح | حفظ المبلغ الفعلي؛ دون شطب أو إغلاق أو حركة جديدة |
| cancel | المتجر المالك أو العمليات | cancelled | قبل خروج النقد فقط؛ تحرير قرار التخصيص |

الإلغاء بعد الخروج ممنوع. لا يُعاد إنشاء رد ثانٍ بعد الإلغاء في هذه الشريحة؛ إعادة فتح القرار وإرجاع نقد لم يستلمه العميل وتسوية النقد المفقود لاحقة. الفرق يبقى مفتوحًا حتى تأكيد استلام كامل القيمة. لا تستخدم الواجهة الصحيحة للتحصيل الأصلي كإثبات أن الرد وصل للعميل.

المبلغ يأتي من لقطة الإرجاع ويتطابق مع تحصيل البضائع، ويثبت في سجل الرد؛ لا يستطيع العميل أو الموظف تغيير قيمته. لا تُكتب قيود مالية عند الطلب أو الحجز. مصدر النقد محصور بقيود `operations_cash` للتحصيل نفسه، وليس بقروض من تحصيل آخر.

## القيود والمطابقة

الخروج: `customer_refund_transit +amount` مقابل `operations_cash -amount`.

إقرار العميل: `merchant_payable +amount` مقابل `customer_refund_transit -amount`.

القيدان مرتبطان بالرد والشحنة، متوازنان ومغلقان وغير قابلين للتحرير أو التكرار. تؤكد `validateCash` الأصل والمبلغ والعملة وعدد القيود والحسابات والحالة. الحركة والحالة والإصدار وسجل التدقيق ونتيجة منع التكرار معاملة واحدة. لا تتحرك البضاعة أثناء الرد المالي ولا تتغير حالة تسليم الشحنة الأصلية.

تعرض شاشة النقد مبلغ رد العملاء المعلّق والمبالغ التي أكدوا استلامها، وتُخفض قيمة البضائع المستحقة للمتاجر عند إقرار العميل فقط. تبقى رسوم التوصيل مستقلة. مبلغ الفرق محفوظ مع محضر الإقرار ولا يُمحى بعد حلّه.

## عقد API لمطوّر Flutter

`CommercialReturn.refund` في `shared/commercial-returns.ts` يحتوي `id`, `status`, `version`, `amountMinor`, `currency`, `issueOpen`, `lastReportedMinor`, `releasedAt`, `confirmedAt`. وتوضح `inspectionComplete` اكتمال فحص القطع. تظهر البيانات ضمن قراءة المرتجعات المقيدة بالدور وطلبات العميل المملوكة لجلسة المتجر.

`POST /api/refunds/:returnId/actions` للحساب التشغيلي: `request`, `reserve`, `release`, `cancel`. البيانات:

```json
{
  "action": "release",
  "expectedVersion": 2,
  "amountMinor": 20000000,
  "currency": "SYP",
  "reference": "إيصال رد 123",
  "reason": "تسليم قيمة البضائع كاملة للعميل"
}
```

الأرقام أعلاه توضيحية؛ يُستخدم المبلغ والإصدار الفعليان. `request` يستخدم إصدار الإرجاع عند عدم وجود رد، وبقية الأفعال تستخدم إصدار الرد نفسه. الطلب من متجر بلا سياق ملكية محدد مرفوض. الأوامر المالية تستخدم `Idempotency-Key` و`X-Financial-Actor` لحماية تغير الحساب.

`POST /api/storefront/orders/:shipmentId/refund` للعميل: `confirm` أو `report`، بنفس الحقول وبإصدار الرد وجلسة `shop`. عند الإبلاغ يُدخل المبلغ المستلم فعليًا، بما فيه صفر. لا يظهر مبلغ استلام عميل آخر أو يسمح بالإقرار عنه.

تُضاف أحداث `refund.request/reserve/release/confirm/report/cancel` إلى سجل المرتجعات للمتجر والعمليات. المندوب لا يقرأ سجلات رد النقد عبر هذا السجل. الفشل يرجع `code`, `message`, `requestId`؛ ويُرفض الإصدار القديم بـ409.

## التعافي والتحقق

إقرارات الحساب التشغيلي تستعمل سجل الاستعادة المالي القائم: حفظ قبل الإرسال، قفل على الحساب، كشف نتيجة بعد إعادة تحميل الصفحة دون تكرار الحركة، وإعادة المحتوى والمفتاح نفسيهما بعد مراجعة. تعمل `/api/financial-commands/status` مع مسار refunds. إقرار العميل يحتفظ بالأمر المعلق في النموذج ويجمد حقوله عند فقدان الرد؛ السجل الدائم لأوامر العميل بين الأجهزة غير منفذ. تحديث القراءة بعد إعادة الفتح يكشف الحالة الخادمية.

- `tests/customer-refunds.test.ts`: شروط الفحص والتمويل، الملكية والقيمة والرسوم، منع التعارض مع الصرف ورجوع الحوالة، فرق العميل، التراجع الذري عند فشل التدقيق، استرداد دفعة المتجر قبل الرد، الإلغاء والاستمرار وإقرار العميل بعد إعادة تشغيل قاعدة مؤقتة.
- `scripts/delivery-ui-check.ts`: قاعدة `memory://` ومنفذ مؤقت، تسليم نقدي ثم إرجاع وفحص وحوالة وقرار وحجز وخروج ورد العميل، وفقد رد خروج النقد مع استعادة بعد إعادة تحميل الصفحة، وفقد رد العميل مع إعادة الأمر، وحصر القيود الجديدة بقيدين فقط، وعرض 1440/390/360.
- اختبارات الترقية السابقة تتضمن إضافة الجدول والعمود دون إعادة تسجيل تحصيل أو صرف قديم.

المصادقة الإنتاجية وإثبات الهوية وقنوات إخطار العميل والدفع الإلكتروني وسياسات الرسوم والأجور والتسويات الجزئية ما زالت خارج هذه الشريحة.
