# خطة تطوير المنصة اللوجستية المستقلة

**تاريخ الإنشاء:** 8 أكتوبر 2026  
**الإصدار:** 0.1  
**الغرض:** مرجع داخلي لتصميم المشروع وتنفيذه ومتابعة تقدمه  
**الحالة:** خطة أولية قابلة للتحديث؛ لا تشير قوائم الإنجاز إلى تنفيذ فعلي قبل توثيق الدليل

## 1. الاتجاه المتفق عليه

نبني منصة لوجستية مستقلة، تدير شبكة مفتوحة من المتاجر والمستودعات ونقاط الاستلام والمندوبين وشركات النقل. تستخدم التطبيقات خدماتها عبر API، ويكون **Tendsy أول تطبيق مستفيد**، ثم تُضاف تطبيقات أخرى دون إعادة بناء منطق التنفيذ لكل تطبيق.

الهدف هو تنفيذ الطلبات بكفاءة وبتكلفة إجمالية منخفضة، مع ضبط المخزون والعهدة والخدمة والتحصيل والتسوية. يستهدف التصميم قابلية التوسع لتشمل سوريا؛ ويُفعّل التشغيل تدريجيًا بحسب جاهزية الشركاء والمسارات والتغطية الفعلية.

نبدأ بتثبيت مفهوم الأعمال ومتطلباته قبل التطوير. لا تُفترض مواعيد أو ميزانية أو تقنية نهائية أو نسب وفر قبل معرفة الحجم والموارد وقياس الأداء.

### العلاقة بالوثائق السابقة

- [WAREHOUSE-LOGISTICS.md](./WAREHOUSE-LOGISTICS.md) يمثل المتطلبات الأولية المرتبطة بـCassion وPIDO، ويُستخدم لاستخراج المتطلبات ومراجعتها، دون توريث قراراته تلقائيًا.
- [LOGISTICS-CONCEPT-TENDSY-EXECUTIVE-AR.docx](./LOGISTICS-CONCEPT-TENDSY-EXECUTIVE-AR.docx) يعرض المفهوم وخطة العمل للإدارة بصيغة تعريفية، دون طلبات موافقة.
- هذا الملف هو مرجع خطة التطوير. عند التعارض، تُتبع توجيهات المستخدم الأحدث والقرارات الداخلية الموثقة، وتُحدث الخطة لتبقى متسقة معها.
- تسمية المنتج النهائية وعلاقة اسم PIDO به لم تُحسما بعد. لا نربط التصميم باسم التطبيق المستفيد.

## 2. حدود المسؤوليات

| المجال | التطبيق التجاري مثل Tendsy | المنصة اللوجستية |
|---|---|---|
| البيع | المنتجات والأسعار والسلة والعميل وطلب البيع | بيانات التغطية وخيارات التنفيذ |
| الخدمة | عرض الخيارات وتسجيل اختيار العميل | فحص الأهلية وتقدير السعر والموعد وصلاحية العرض |
| التنفيذ | إرسال الطلب المعتمد والتعديلات المطلوبة | الحجز والتجهيز والشحن والإسناد والمتابعة |
| المخزون | عرض المتاح للبيع وفق المصدر المعتمد | إدارة مخزون المستودعات الواقعة ضمن خدمة المنصة ومزامنة المتاح |
| الإلغاء والإرجاع | القرار التجاري والتواصل مع العميل | تحديد إمكانية الإجراء وتنفيذه وإبلاغ النتيجة |
| الأموال | الدفع الإلكتروني وقرار الاسترداد وفق التكامل المحدد | التحصيل عند الاستلام وعهدة الأموال ورسوم الشركاء وتسوياتها |
| الدعم | التواصل التجاري مع العميل | أدلة التشغيل ومعالجة الاستثناءات بحسب سياسة المسؤوليات |

**قاعدة أساسية:** لا تكون هناك جهتان مستقلتان تملكان قرار الحجز للمخزون نفسه. يُحدد مصدر مرجعي لكل مخزون وحالة وبيان مالي، وتوثق معالجة اختلاف البيانات.

## 3. الخدمات والنطاق الأول

### الخدمات المستهدفة

1. نقل وتسليم طرد جاهز من متجر أو موقع منشأ.
2. تخزين المنتجات وحجزها وتجهيزها ثم نقلها وتسليمها.
3. التسليم إلى عنوان أو نقطة استلام مشاركة.
4. النقل بين المدن عبر مراحل وشركاء متعددين.
5. إعادة محاولة التسليم والإرجاع إلى الجهة الصحيحة.
6. تحصيل الدفع عند الاستلام ومتابعة المستحقات والتسويات.

### نطاق التجربة المقترح

تبدأ التجربة بـTendsy وطلب تنفيذ واحد أو أكثر لكل طلب بيع، ضمن شركاء ومناطق ومسارات محددة. تشمل دورة مكتملة: طلب الخدمة، وقبول التنفيذ، والاستلام، والنقل، والتسليم أو الفشل والإرجاع، والتحصيل والتسوية عند انطباقهما.

المسار الأول المقترح هو **نقل الطرود الجاهزة**، لأنه يقلل الاعتماد على إدارة المخزون. إذا كانت خدمة المستودعات ضرورية لإطلاق Tendsy، يُضاف الحجز والتجهيز إلى الإصدار الأول ويُحدّث نطاقه قبل التطوير. يبقى هذا اختيارًا مفتوحًا لا قرارًا نهائيًا.

ندعم في التصميم مراحل النقل بين المدن منذ البداية، ويمكن اختبار مسار محدد في التجربة. لا تعني قابلية التوسع تفعيل جميع المدن أو الخدمات في الإصدار الأول.

### خارج النطاق الأول

- بناء متجر إلكتروني أو سلة أو نظام عروض بدل Tendsy.
- بناء نظام محاسبة مؤسسي شامل أو بوابة دفع جديدة.
- تفعيل جميع شركات الشحن أو جميع التطبيقات دفعة واحدة.
- ضمان الحل الأمثل رياضيًا لكل حالة أو البدء بتوقعات تعتمد على بيانات غير متوفرة.
- التتبع المستمر في الخلفية قبل تحديد واجهة المندوب وإمكاناتها واحتياجات التشغيل.

## 4. مبادئ التصميم التي تحكم التنفيذ

- **استقلال التطبيق:** لا يعتمد نموذج التشغيل على أسماء حالات Tendsy أو جداول قاعدة بياناته؛ توضع المطابقة في التكامل.
- **عزل الأطراف:** تُفصل هوية التطبيق المتصل عن هوية المتجر والشريك. المشاركة في عملية تمنح الوصول اللازم لتلك العملية فقط.
- **سلامة العمليات:** تكرار الطلب أو الحدث لا ينشئ شحنة أو حجزًا أو قيدًا ماليًا إضافيًا.
- **فصل الحالات:** حالة الشحنة لا تختزل حالة طلب البيع أو التسوية المالية أو مزامنة التطبيق.
- **قابلية التدقيق:** كل تغير مؤثر يسجل الفاعل والوقت والسبب والمرجع.
- **تقليل التكلفة:** يُقاس أثر القرار على السلسلة كاملة، مع إبقاء القيود الإلزامية سليمة.
- **التغطية الواقعية:** تُقبل الخدمات عند وجود مسار وسعة وشروط تشغيل قابلة للتحقق.
- **التدخل التشغيلي:** يمكن تعديل الخطة ضمن الصلاحيات، مع تسجيل السبب وإعادة التحقق من القيود.
- **تحمل الأعطال:** توجد مسارات واضحة لإعادة المحاولة والتعويض والمطابقة ومعالجة المهام العالقة.
- **بساطة البنية:** نبدأ بوحدات واضحة وبنية تشغيل محدودة؛ لا نفصل خدمات مستقلة قبل وجود حاجة مقاسة.

## 5. مراحل التطوير والمخرجات ومعايير الإنجاز

### المرحلة 0 — تثبيت متطلبات الأعمال

**المخرجات:** مواصفات أعمال، ومصفوفة مسؤوليات، وسيناريوهات تشغيل، وسجل قرارات.

- [ ] تعريف الجهات المشاركة: مشغل المنصة، التطبيق، المتجر، الشريك، الموقع، السائق، المركبة.
- [ ] تحديد نموذج تفعيل الشركاء، وتوثيق قدراتهم ومسؤوليات الطرود والأموال.
- [ ] تحديد مصدر البيانات وصلاحيات تعديلها لكل مجال.
- [ ] تحديد خدمات Tendsy المطلوبة للإطلاق ونطاق التجربة.
- [ ] رسم سيناريو داخل مدينة، وسيناريو بين مدينتين مع دفع عند الاستلام وفشل التسليم.
- [ ] تحديد الإلغاء وتعديل الوجهة وإعادة المحاولة والإرجاع والتلف والفقد والاعتراضات.
- [ ] تحديد قواعد العملة والأسعار ورسوم الشركاء والتسوية.
- [ ] توثيق المدخلات المتوقعة: الحجم، أوقات الخدمة، السعات، وجود اتصال، وموارد الفريق.

**معيار الإنجاز:** لكل سيناريو بداية ونهاية ومسؤول واضح، وانتقالات حالة وآثار على الطرد والمخزون والأموال، مع تمييز القرارات المفتوحة.

### المرحلة 1 — النموذج التشغيلي وعقد التكامل

**تعتمد على:** المرحلة 0 بالقدر اللازم للخدمة المختارة.

**المخرجات:** نموذج نطاق، ومخططات حالات، ومواصفة API، وعقد أحداث، ومحاكاة تكامل مع Tendsy.

- [ ] تعريف الكيانات والعلاقات والمعرفات الخارجية والداخلية.
- [ ] فصل حالات التنفيذ والشحنة والمهمة والمالية والمزامنة.
- [ ] تحديد المدخلات الإلزامية وأخطاء الأعمال وقواعد تعديل الطلب.
- [ ] تحديد عرض الخدمة: صلاحيته، وما إذا كان يتضمن حجز سعة أو مخزون، ومتى يعاد التحقق منه.
- [ ] تحديد توقيت الدفع والحجز وقبول التنفيذ والتعويض عند الفشل.
- [ ] تعريف منع التكرار ومطابقة payload عند إعادة استخدام المفتاح نفسه.
- [ ] تعريف Webhooks وتوقيعها وتسلسل الأحداث والإصدارات وإعادة المحاولة والمطابقة.
- [ ] بناء أمثلة طلبات ونتائج ومحاكاة تفيد فريق Tendsy قبل اكتمال التنفيذ.

**معيار الإنجاز:** يمكن لفريق التطبيق تنفيذ دورة الربط باستخدام العقد والمحاكاة، بما يشمل التكرار والأخطاء والإلغاء، دون معرفة تفاصيل قاعدة بيانات المنصة.

### المرحلة 2 — أساس المنصة وإدارة الشبكة

**تعتمد على:** النموذج والصلاحيات وعقد الهوية في المرحلة 1.

**المخرجات:** تطبيق أساسي قابل للتشغيل، وإدارة الأطراف والمواقع والخدمات، وسجل تدقيق، ومسار نشر ومراقبة.

- [ ] إنشاء هيكل المشروع وبيئات التطوير والاختبار والتشغيل وإدارة الأسرار.
- [ ] تعريف حسابات التطبيقات ومفاتيح الوصول ونطاقات الصلاحيات.
- [ ] إدارة المتاجر والشركاء والمواقع والمركبات والسائقين والتحقق من أهلية الخدمة.
- [ ] تعريف مناطق الخدمة ومسارات النقل وساعات العمل والسعات وشروط الطرود.
- [ ] تطبيق عزل البيانات على الاستعلامات والتعديلات والتقارير والوظائف الخلفية.
- [ ] إضافة سجل تدقيق وحماية البيانات الخاصة ومراجع التتبع العامة.
- [ ] إنشاء معالجة خلفية للأحداث والإشعارات مع قائمة أعطال قابلة لإعادة التشغيل المنضبط.
- [ ] إعداد المراقبة والنسخ الاحتياطي وتجربة الاستعادة والترحيلات.

**معيار الإنجاز:** تنجح دورة تفعيل شريك وموقع وخدمة؛ وتثبت اختبارات الصلاحيات منع الوصول غير المصرح، مع استعادة نسخة احتياطية في بيئة اختبار.

### المرحلة 3 — دورة التنفيذ الأساسية والتكامل الفعلي مع Tendsy

**تعتمد على:** المرحلتين 1 و2.

**المخرجات:** دورة نقل مكتملة، وواجهات تشغيل، وتكامل فعلي، وتقارير أولية.

- [ ] تقديم خيارات خدمة قابلة للتنفيذ وفق تغطية وسعة وتسعير مهيأ.
- [ ] قبول طلب التنفيذ مرة واحدة وربطه بطلب Tendsy.
- [ ] إنشاء الشحنات ومهام النقل ومراحلها، وإسنادها يدويًا أولًا مع فحص الأهلية.
- [ ] تنفيذ الاستلام وانتقالات العهدة والوصول والتسليم وإثباته.
- [ ] إدارة نقاط الاستلام ورمز التسليم إن كانت ضمن النطاق المختار.
- [ ] تنفيذ الإلغاء والفشل وإعادة المحاولة والإرجاع، مع منع الانتقالات غير المسموحة.
- [ ] إنشاء وتتبع المطالبات التشغيلية المرتبطة بالفقد أو التلف عند وقوعها.
- [ ] تفعيل التتبع الخاص والعام مع تقليل البيانات المعروضة وسياسة صلاحية الموقع.
- [ ] إرسال أحداث Tendsy وإعادة إرسال الفاشل وإجراء المطابقة.
- [ ] توفير لوحة تشغيل للشحنات العالقة والأخطاء والإجراءات اللازمة.

**معيار الإنجاز:** يمر طلب من Tendsy حتى التسليم، وطلب آخر حتى الإرجاع، وتنعكس النتائج في التطبيق؛ ولا يؤدي تكرار API أو Webhook إلى تكرار التنفيذ.

### المرحلة 4 — المخزون والتحصيل والتسوية

**تعتمد على:** كيانات المرحلة 1 والأساس في المرحلة 2 ودورة المرحلة 3. يمكن تطويرها قبل اكتمال المرحلة 3 بعد استقرار العقود.

**المخرجات:** دورة مالية تشغيلية مكتملة؛ ودورة مخزون مكتملة إذا كانت خدمة المستودعات ضمن الإصدار.

**مسار المخزون عند تفعيل الخدمة:**

- [ ] تسجيل الوارد والصادر والنقل والجرد والتالف، وربط الوحدات والمنتجات بكل متجر.
- [ ] فصل الموجود فعليًا والمتاح والمحجوز والمجهز والموجود قيد النقل.
- [ ] تنفيذ حجز ذري مع مدة صلاحية وتحرير أو استهلاك محدد عند كل حالة.
- [ ] إدارة التجهيز والطلبات المقسمة والتأكيد من مستودع خارجي وعدم استجابته.
- [ ] معالجة الإرجاع: فحص الحالة قبل إعادة الكمية إلى المتاح للبيع.
- [ ] مزامنة المتاح وإجراء المطابقة مع Tendsy ومصادر المخزون الأخرى.

**المسار المالي:**

- [ ] فصل سعر العميل وأجر الشريك ورسوم المنصة والتكلفة الفعلية.
- [ ] تسجيل التحصيل والدفع المسبق عند انطباقهما دون الخلط بينهما.
- [ ] تتبع انتقال عهدة الأموال والمبالغ المعلقة وفروق التحصيل.
- [ ] إنشاء مستحقات قابلة للتدقيق وتسويات تؤكد الاستلام الفعلي.
- [ ] منع تكرار التسجيل المالي، ومعالجة التصحيح بعكس أو قيد تعويضي مرتبط بالأصل.
- [ ] تحديد أثر الإلغاء والإرجاع والنزاع على الرسوم والتحصيل والاسترداد.
- [ ] تسجيل كل مبلغ مع عملته ودقة مناسبة، ومنع المقاصة بين عملات مختلفة دون سياسة تحويل محددة.

**معيار الإنجاز:** لا ينتج الحجز المتزامن عن بيع كمية غير متاحة؛ ولا تسجل العملية المالية مرتين؛ وتكتمل مطابقة نموذجية بين التحصيل والعهدة والمستحقات والتسوية. يشترط إكمال هذا المسار قبل تشغيل COD بأموال فعلية.

### المرحلة 5 — التحسين وقياس الكفاءة

**تعتمد على:** نموذج تشغيل وبيانات تكلفة وسعة موثوقة من المراحل السابقة. يبدأ جمع البيانات والمحاكاة مبكرًا.

**المخرجات:** خطة مرجعية، ومحرك تحسين قابل للقياس، وأسباب اختيار قابلة للفحص، وتدخل يدوي آمن.

- [ ] بناء خطة مرجعية بسيطة قابلة للتنفيذ للمقارنة.
- [ ] تعريف دالة التكلفة والقيود الإلزامية والأهداف المرنة وأولوياتها.
- [ ] تحسين اختيار مصدر التجهيز وتقسيم الطلب عند تفعيل المستودعات.
- [ ] تجميع المهام وإسنادها وترتيبها وفق السعة ومواعيد الخدمة والاستلام قبل التسليم.
- [ ] التعامل مع مراحل النقل بين المدن والجداول ومواعيد التحويل والسعة المتاحة.
- [ ] دعم الطلبات الجديدة والتأخير والتعطل دون تغيير ما نُفذ فعليًا.
- [ ] تحديد مهلة للحساب وخطة بديلة سليمة عند عدم وجود حل أو تجاوز المهلة.
- [ ] تشغيل الخطط المقترحة للمقارنة دون تطبيقها أولًا، ثم تفعيلها تدريجيًا.
- [ ] قياس تكلفة الحساب وخدمات الخرائط إلى جانب وفر التشغيل.

**معيار الإنجاز:** جميع الخطط المطبقة تحترم القيود الإلزامية، وتظهر نتائج المقارنة على مجموعة سيناريوهات موثقة. تُحدد أهداف التحسن بعد قياس خط الأساس، مع التحقق من عدم تدهور الخدمة.

### المرحلة 6 — التجربة التشغيلية والتوسع

**تعتمد على:** دورة مكتملة للخدمات المفعلة، ونجاح الاختبارات والتعافي، وجاهزية الشركاء.

**المخرجات:** تقرير نتائج التجربة، وتحسينات مثبتة، وخطة توسع مبنية على السعة والأداء.

- [ ] تجربة مسار محلي ومسار بين مدينتين ضمن التغطية المختارة، بحسب الخدمات المفعلة.
- [ ] تدريب المشاركين وإعداد إجراءات الفشل والنزاعات والتسوية والدعم.
- [ ] قياس أحجام العمليات والأخطاء والكلفة وزمن التنفيذ والمزامنة.
- [ ] اختبار انقطاع الاتصال، وتعطل الإشعارات، وتعطل عامل خلفي، واستعادة البيانات.
- [ ] معالجة نتائج التجربة قبل إضافة مناطق أو شركاء جدد.
- [ ] إضافة تطبيق ثانٍ لإثبات استقلال النموذج عن Tendsy.
- [ ] مراجعة البنية عند وجود اختناق مقاس، ثم فصل المكونات التي تحتاج استقلالًا فعليًا.

**معيار الإنجاز:** تعمل الدورة التشغيلية والمالية للخدمات المختارة دون فجوات غير معالجة، وتوجد مراقبة وإجراءات استجابة؛ ولا تُفعّل منطقة جديدة قبل إثبات مسار الخدمة وسعته ومسؤولياته.

### قواعد الحالات

- تُكتب لكل كيان آلة حالات مستقلة؛ لا تُستخدم قائمة حالة واحدة لجميع الكيانات.
- لكل انتقال فاعل مسموح وشروط مسبقة وأثر على السعة والعهدة والمخزون والمالية.
- رفض طلب الإلغاء بعد انتقال معين يعيد سببًا واضحًا، وقد يحوله إلى مسار إرجاع.
- تُحدد قواعد تجميع حالة الطلب عند التسليم الجزئي أو فشل بعض الشحنات.
- تُحفظ أوقات حدوث الأحداث وأوقات استقبالها، وتُعالج الأحداث المتأخرة وفق إصدار الكيان.
- لا تساوي حالة «تم التسليم» حالة «تمت التسوية» أو «تمت مزامنة التطبيق».

## 7. عقد التكامل مع Tendsy

هذه قدرات مطلوبة للعقد؛ تُحدد المسارات والحقول النهائية في مواصفة API خلال المرحلة 1.

| القدرة | المدخلات الأساسية | النتيجة |
|---|---|---|
| خيارات الخدمة | المنشأ أو المنتجات، الوجهة، الوزن والحجم، مستوى الخدمة | الخيارات والسعر والعملة والموعد وصلاحية العرض |
| إنشاء التنفيذ | مرجع البيع، المتجر، البنود أو الطرود، الخدمة، بيانات التسليم والتحصيل | معرف داخلي ونتيجة قبول أو رفض معللة |
| الاستعلام | معرف داخلي أو مرجع خارجي ضمن هوية التطبيق | الحالة والشحنات والأحداث المسموح بعرضها |
| الإلغاء أو التعديل | مرجع العملية والسبب والتغيير المطلوب | قبول الإجراء أو رفضه مع حالة التنفيذ الفعلية |
| الإرجاع | البنود أو الطرود والسبب والوجهة | طلب إرجاع ومسار حالاته |
| المخزون عند تفعيله | المنتجات والمواقع ومراجع المصدر | المتاح والحجز والمطابقة وفق الصلاحيات |
| النتائج المالية | مرجع العملية والفترة والصلاحيات | التحصيل والمستحقات والتسوية والفروق |
| الأحداث | اشتراكات التطبيق ووجهة الإشعار | أحداث موقعة ذات معرف وإصدار قابلين للمطابقة |

### متطلبات موثوقية التكامل

- نطاق مفتاح منع التكرار يشمل هوية التطبيق ونوع العملية، وتُحدد مدة حفظه.
- إعادة المفتاح نفسه بمحتوى مختلف تعيد تعارضًا؛ وانقطاع الاستجابة يعالج بالاستعلام أو إعادة الطلب الآمنة.
- يرتبط المرجع الخارجي بالتطبيق والمتجر وفق العقد، دون افتراض أنه فريد عالميًا.
- يُحفظ الحدث مع التغيير التشغيلي بصورة متسقة، ثم يرسله عامل خلفي.
- تُعالج الإشعارات كتسليم قد يتكرر؛ لا يُفترض ضمان وصولها مرة واحدة أو بالترتيب دائمًا.
- توجد توقيعات، وحدود إعادة محاولة، وتراجع زمني، وإدارة أعطال، ومطابقة دورية.
- تُحدد قواعد الإصدارات والإيقاف التدريجي للعقود القديمة وحدود الطلبات والتصفح.
- لا تُعرض بيانات عميل أو شريك لطرف لا يحتاجها لتنفيذ مهمته.

## 8. نهج التحسين

### الهدف والقيود

نقارن خططًا قابلة للتنفيذ وفق **التكلفة الإجمالية المتوقعة**، التي تجمع التجهيز والمناولة والنقل ووقت الموارد وتقسيم الشحنات والانتظار، وتضيف تكلفة التأخير المرن وإعادة المحاولة عند وجود بيانات معتمدة.

القيود الإلزامية لا تتحول إلى غرامات تسمح بتجاوزها. تشمل عدم تجاوز المخزون أو السعة، وتوافق الخدمة والمركبة، وتسلسل الاستلام قبل التسليم، والتغطية، وساعات العمل، والموعد الصارم عندما تنص الخدمة عليه. يُحدد أثر الطلبات التي لا يمكن تنفيذها بدل إخفائها أو إسقاطها من النتائج.

### ترتيب إدخال قدرات التحسين

1. فحص الأهلية واستبعاد الخيارات غير القابلة للتنفيذ.
2. خطة مرجعية مع تكلفة محسوبة وتفسير واضح.
3. تجميع المهام وتحسين الإسناد وترتيب الزيارات.
4. تنسيق التحويلات بين المدن ومواعيد وسعات مراحل النقل.
5. تحسين مصدر التجهيز والمخزون وتقسيم الطلب عند تفعيل التخزين.
6. إعادة التخطيط عند التغييرات، مع تثبيت المنفذ والالتزامات القريبة وتسجيل تعديل الخطة.
7. تخطيط إعادة توزيع المخزون والتوقعات بعد توفر بيانات كافية لإثبات الحاجة.

تُختار فئة الحل المناسبة بعد توصيف المسألة؛ قد تشمل مسائل الإسناد وتدفق الشبكة ومسارات المركبات ذات السعات والنوافذ الزمنية. لا نختار خوارزمية واحدة لجميع القرارات ولا نلتزم بمكتبة قبل مقارنة متطلبات الحجم والزمن والترخيص والتشغيل.

تعتمد الخطة على زمن ومسافة الطريق أو تقدير موثق، لا على المسافة الجوية وحدها. يُحدد مصدر بيانات الطرق وكيفية تخزين النتائج وإعادة استخدامها وحدود صلاحيتها. عند غياب البيانات لا نعرض موعدًا دقيقًا غير مدعوم، ونستخدم خدمة مشروطة أو مراجعة تشغيلية وفق السياسة.

## 9. البنية التقنية المقترحة

الاقتراح الأولي هو تطبيق مركزي بوحدات منفصلة منطقيًا، وقاعدة بيانات معاملية، وعمال خلفية للربط والإشعارات والتحسين، مع واجهات API موثقة. لا يمثل ذلك اختيارًا نهائيًا للغة أو إطار عمل أو مزود استضافة.

الوحدات: الهوية والصلاحيات، والشركاء والشبكة، والخدمات والتسعير، والتنفيذ، والمخزون، والتخطيط، والعهدة والإثباتات، والمالية، والتكامل، والإشعارات، والتقارير.

واجهات التشغيل المطلوبة: إدارة الشبكة، ولوحة المتجر أو الشريك، وواجهة المستودع عند تفعيله، وواجهة المندوب، وصفحة تتبع للعميل. يُحدد تطبيق الويب أو الهاتف للمندوب بعد حسم الاتصال والتتبع والعمل دون شبكة.

تعتمد المكونات الخارجية مثل الخرائط والبريد والرسائل والدفع على واجهات قابلة للاستبدال. يتأثر السعر والموعد المتوقع بالمسار التشغيلي، بينما يُفصل اختيار مزود الإشعار عن قواعد العمل.

## 10. التحقق ومعايير الجودة

| المجال | السيناريوهات التي يجب إثباتها |
|---|---|
| العزل والصلاحيات | منع قراءة أو تعديل بيانات طرف آخر عبر API والواجهة والأحداث والتقارير |
| الحجز والسعة | طلبات متزامنة، انتهاء الحجز، إعادة الطلب، وعدم تجاوز الكميات أو السعات |
| الحالات | أحداث متأخرة، إلغاء أثناء النقل، إعادة إسناد، تسليم جزئي، وإرجاع |
| التكامل | تكرار الطلب، اختلاف المحتوى، انقطاع الاستجابة، فشل Webhooks، والمطابقة |
| المال | تحصيل مكرر، فرق مبلغ، انتقال عهدة، تسوية جزئية، عكس قيد، وعملات مختلفة |
| التحسين | خطة غير ممكنة، نقص بيانات، تجاوز زمن الحساب، تعطل مركبة، والتحقق من كل قيد |
| الاتصال | تسجيل حدث دون شبكة ثم مزامنته، منع تكراره، ومعالجة تضارب التعديلات |
| التشغيل | توقف عامل، إعادة تشغيل، استعادة نسخة، وطلب عالق مع سبب قابل للتشخيص |

تُختار اختبارات وحدات وتكامل ونهاية إلى نهاية وفق المخاطر، مع سيناريو ربط كامل مع Tendsy. ويُختبر الحمل على أحجام مستمدة من توقعات التشغيل، لا أرقام اعتباطية.

### مؤشرات المتابعة

- تكلفة الشحنة المكتملة، مع تعريف توزيع تكلفة الفشل والإرجاع عليها ومكونات التكلفة المتاحة.
- نسبة التسليم ضمن الموعد ونجاح المحاولة الأولى.
- زمن التجهيز والانتظار والنقل والتحويل بين المراحل.
- الكيلومترات لكل شحنة واستغلال المركبات والمواقع.
- دقة المخزون والحجوزات المنتهية وفروق الجرد.
- قيمة وعمر الأموال غير المسواة وفروق التحصيل.
- زمن مزامنة التطبيق، وأخطاء التكامل، وتراكم المهام الخلفية.
- زمن حساب الخطة، وجودتها، وتكلفة خدمات الخرائط والإشعارات والبنية.

لكل مؤشر تعريف ومصدر ونافذة زمنية وتقسيم حسب الخدمة والمنطقة. تُحدد الأهداف بعد قياس خط الأساس.

## 11. سجل القرارات المفتوحة

هذه مسائل تصميم داخلية؛ لا تمثل طلبات للإدارة أو شروطًا لتعطيل جميع الأعمال. يُحسم كل قرار قبل بدء الجزء الذي يعتمد عليه، وتستمر الأعمال المستقلة.

| الرمز | القرار | متى يلزم حسمه |

| D02 | خدمة Tendsy الأولى: طرد جاهز أم تخزين وتجهيز أيضًا | قبل تثبيت نطاق الإصدار الأول |
| D03 | ملكية المخزون وتوقيت الدفع والحجز وآلية التعويض | قبل تطوير الحجز وربط الشراء |
| D04 | العملات والتسعير والرسوم وحدود التحصيل والتسوية | قبل تنفيذ المسار المالي |
| D05 | مناطق ومسارات التجربة والسعات ومواعيد الخدمة | قبل تهيئة التشغيل واختبار الأداء |
| D06 | تعدد المتاجر في طلب Tendsy وقواعد التقسيم وتجميع الحالة | قبل تثبيت عقد التنفيذ |
| D07 | نوع واجهة المندوب ومستوى العمل دون اتصال والتتبع | قبل تطوير واجهة الميدان |

| D09 | مصادر الحجم المتوقع وحجم الفريق والبنية التقنية والاستضافة | قبل تقدير الجدول والموارد |

يسجل القرار المنتهي مع تاريخه والسبب والبدائل وأثره، ويُحدّث القسم المتأثر في الخطة. لا يتحول الاقتراح تلقائيًا إلى قرار لمجرد بدء العمل.

## 12. أول قائمة عمل

## 13. إدارة المرجع ومتابعة التقدم

- تحدّث مربعات الإنجاز فقط بعد اكتمال المخرج ومعيار القبول، مع رابط إلى دليل التنفيذ أو الاختبار.
- يسجل كل تغيير في النطاق وسببه وأثره على التكامل والتكلفة وترتيب المراحل.
- تُربط المهام بالمرحلة والقرار الذي تعتمد عليه؛ وتُفصل المهام المنجزة عن المقترحة والمؤجلة.
- لا يبدأ جزء يعتمد على قرار غير محسوم بافتراض صامت؛ يُوثق افتراض قابل للمراجعة وحدود استخدامه.
- لا تُضاف خدمات أو مناطق تشغيل لمجرد وجود دعم نظري لها في النموذج.
- لا تُكرر الاختبارات المستقرة إلا عند تغيير ذي صلة أو ظهور خلل أو خطر غير محسوم.
